# Phase 3 — Ability Framework + First Two Abilities (GDD M2)

**Goal:** a framework that makes the `CHARACTER-SPEC.md` grammar enforceable in code, then two abilities by two different owners built on it.

**Gate question:** *Does the ability grammar survive contact with two people designing independently?*

## Framework
- `Ability` base class (server-authoritative) with enforced lifecycle:
  `input → tell (audio + VFX, ≥0.3s) → effect → end → cooldown`.
  The base class **refuses** a tell shorter than `Tuning.min_tell_time` (0.3s) and control durations > 1.0s — the hard rules live in code, not in reviews.
- `AbilityDef` resource: archetype slot (enum of 8), power budget (strong / weak from `damage · movement · control · information`), cooldown 12–25s or charges, tell sound, tell VFX scene.
  - Numbers in `AbilityDef` are read from the central tuning file keyed by ability id — owners edit shape, not strength (CHARACTER-SPEC Part 4).
- `CharacterDef` resource: name, owner, colour, silhouette scene, passive quirk, voice lines (kill / death / parry), death animation.
- Shared-kit helpers abilities may use: apply_displacement, apply_slow (≤1s), spawn_zone, spawn_trap, reveal. No ability may add new resources/stats/UI (hard ban).
- Killfeed shows ability name as the kill method.
- Validator tool (editor script): scans all `AbilityDef`s and flags slot collisions, out-of-range cooldowns, missing tells, missing counterplay text.

## Tasks
- [x] **Ability base class, `AbilityDef`, `CharacterDef`, validator.** `abilities/Ability.cs` enforces the lifecycle (input → tell ≥ `Tuning.MinAbilityTellTime` → effect → cooldown) in code — `TryActivate()` literally refuses to start an ability whose tuning numbers break the grammar (tell too short, cooldown outside 12–25s), rather than relying on a reviewer to catch it. `abilities/AbilityDef.cs` / `CharacterDef.cs` are real Godot Resources (built directly in C#, see below, not hand-authored `.tres`). `abilities/AbilityValidator.cs` scans every registered character for slot collisions, power-budget issues, missing tell/counterplay text, and out-of-range cooldowns — runs automatically every boot (`core/Net.cs`), not just on demand.
- [ ] **Character select screen — not built, same reasoning as Phase 2's melee UI gaps.** Replaced with a `--character=<id>` CLI flag (`core/Net.cs`), which is what the Makefile's `CHARACTER=` var now passes through on `run-client`/`run-local`/`run-bots`. An unknown/omitted id falls back to the registry's first character rather than erroring — verified with a bot that deliberately passed `--character=doesnotexist`.
- [x] **Spec template + two filled specs.** `characters/_template/SPEC.md` (copied from the root `CHARACTER-SPEC.md` Part 2). `characters/blink/SPEC.md` and `characters/firepatch/SPEC.md` are filled in — **honestly labeled as Claude-authored framework examples, not real character submissions** (see the note at the top of each file and in `abilities/CharacterRegistry.cs`). Per Pillar 3, a real character needs a real developer's own concept; these exist only to prove the grammar survives an actual implementation, and should be replaced, not built on, once real developers claim the Mobility/Zone Denial slots.
- [x] **Two example abilities, built and reviewed against the 7-question gate.** Blink (Mobility: `abilities/BlinkAbility.cs`, instant 6m reposition after a 0.3s tell) and Fire Patch (Zone Denial: `abilities/FirePatchAbility.cs`, an 8m-thrown 2.5m-radius zone dealing 20 dmg/sec for 4s). Both pass the mechanical checks (archetype/budget/tell/cooldown/counterplay-text) via `AbilityValidator`; the two review-gate questions that need a human (4: is the tell audible; 6: recognisable from silhouette/audio) are answered **honestly as "not yet" in both SPEC.md files** — there's no audio asset and no silhouette shape difference yet, only a colour. Not glossed over.
- [x] **Playtested with both abilities in a real match.** Headless bots (one per character, later 4 bots split 2/2) on a local server: names sync correctly, correct character colours/abilities equip, `--character=doesnotexist` falls back cleanly, a kill landed via melee and the Fire Patch DoT was independently verified to actually deal damage (137 logged ticks at the expected 0.67 dmg/tick = 20/sec ÷ 30 ticks/sec, removed after confirming). Zero errors across all runs.

## Bug found and fixed while wiring this up
**Not a Phase 3 bug, but caught only because character identity needed to sync**: display names (and now character/ability choice) were never actually reaching other clients. `Main.SpawnPlayer` set `NameLabel.Text` as a plain property mutation on the *server's own copy* of a spawned node — `MultiplayerSpawner` replicates node *creation*, not property changes made after spawn, so every other client's copy of that node kept the scene's default text forever. This silently broke the Phase 2 killfeed/scoreboard names and the floating 3D name label for real multiplayer the whole time — never caught because headless bot testing can't see UI, and the two visible-only pieces were flagged as "not visually verified" in the Phase 2 notes. Fixed with a proper identity handshake (`Player.AnnounceIdentity` client→server, `Player.ReceiveIdentity` broadcast server→all, same `CallLocal=true` broadcast pattern as `BroadcastKill`) that now also carries the chosen character id.

## Playtest questions
- Is each tell audible in a crowd with other things going off? **Not yet answerable** — no audio asset for either ability. Genuinely open, not assumed.
- Can victims name the ability that killed them? **Mechanically yes** — killfeed already shows the ability's `DisplayName` as the kill method (verified: Fire Patch deals damage via the same `ServerApplyDamage(amount, attackerId, method)` path as melee, so "X killed Y (Fire Patch)" falls out for free). Needs a human to confirm it *reads* that way, not just that the string is correct.
- Did either owner need a new shared system? No — both built entirely on the shared kit (`ServerSweep` — originally `ServerTeleport`, replaced once a raw teleport proved able to land players inside geometry — and `SpawnDamageZone`/`AbilityZone`) that now exists for the next ability to reuse too, per CHARACTER-SPEC.md Part 1's "raise it as a proposal separately" rule (nothing was raised because nothing was needed).
